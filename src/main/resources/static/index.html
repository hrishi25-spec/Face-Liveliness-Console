Diagnostic mode is opt-in (mosip.liveness.diagnostics-enabled, off by default) and local only: GET /api/v1/diagnostics answers loopback callers while enabled and the same 404 otherwise, so this section appears only when both hold. It shows raw per-frame scores, timings, FPS and the scorer delegate for troubleshooting (orchestration spec §10) — no pixels are ever retained, and responses are no-store.

Request budget

No limited requests yet.

The service publishes X-RateLimit-Limit, -Remaining and -Reset on session creation and on frame / challenge / extra-check submissions. Capture faster than the window and the frame budget empties — the console shows the limiter running down before the 429 arrives.

Config policy

Saving issues a PUT with the admin key; loading is an open GET. The key stays in this tab's sessionStorage — it is never written to the decision log, and the field shows only a masked tail so a screen share or screenshot can't leak it.

Policy change history

No policy changes recorded yet.

Every PUT to /api/v1/config/{workflow} is recorded with the fields that moved, their previous and new values, and a fingerprint of the admin key that made the change, shown next to each entry so it is clear at a glance which key did the edit. Edits that lower the passive threshold or switch liveness off are marked [risk: HIGH], with the reason. The history loads with the page, so the most recent edit is visible without clicking refresh.

Chain integrity

Checking chain…

The config audit trail is tamper-evident — each entry is hashed over its predecessor (prev_hash → entry_hash). The endpoint verifies the whole chain, so a break beyond the visible audit-feed page is still detected. The header badge is green when every link checks out, amber while a previous key is configured for verification, and red on a tamper or a missing row. The details show whether any historical entries still need the previous key.
