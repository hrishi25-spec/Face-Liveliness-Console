Limitation — the service has no session-list endpoint. It exposes POST /sessions, GET /sessions/{id} and POST /sessions/{id}/close and nothing that enumerates sessions, so this list is exactly what this browser tab created: the ids are held in memory and are gone on reload, and a session created in another tab, on another device or by another person cannot be seen or opened here. A session the tab has forgotten stays open server-side until something closes it or it expires, and a session created with a subjectRef additionally needs that same X-Subject-Ref header on every read. Opening a row reads that session and its audit trail with the two GETs that do exist.

Diagnostics — raw scores

No frames recorded yet.

Diagnostic mode is opt-in (mosip.liveness.diagnostics-enabled, off by default) and local only: GET /api/v1/diagnostics answers loopback callers while enabled and the same 404 otherwise, so this section appears only when both hold. It shows raw per-frame scores, timings, FPS and the scorer delegate for troubleshooting (orchestration spec §10) — no pixels are ever retained, and responses are no-store.

Diagnostics are unavailable here: either diagnostic mode is off or this page is not a loopback caller. Enable mosip.liveness.diagnostics-enabled and open the console on localhost — the two cases answer the identical 404, so this panel cannot (and does not try to) tell them apart.

Config policy

Operator Notice: You are viewing policy details in read-only mode. You do not have authority to modify or save policies.

Saving issues a PUT that the server authorises from your signed-in session; loading is an open GET. The console asks for a username and password in a prompt when a save needs them — never in the DOM, so there is no field to screenshot or screen-share, and never in storage — and the session it receives is held by the browser in an HttpOnly cookie that this page cannot read. Sign out ends the session, and so does Switch role, which hands the workstation to the next person.

Every PUT to /api/v1/config/{workflow} is recorded with the fields that moved, their previous and new values, and a username that made the change, shown next to each entry so it is clear at a glance which account did the edit. Edits that lower the passive threshold or switch liveness off are marked [risk: HIGH], with the reason. The history loads with the page, so the most recent edit is visible without clicking refresh.

Chain integrity

Checking chain…

The config audit trail is tamper-evident — each entry is hashed over its predecessor (prev_hash → entry_hash). The endpoint verifies the whole chain, so a break beyond the visible audit-feed page is still detected. The header badge is green when every link checks out, amber while a previous key is configured for verification, and red on a tamper or a missing row. The details show whether any historical entries still need the previous key.

GET /api/v1/eval/threshold-sweep?targetBpcer=… sweeps the passive threshold over the same median-window decision the live path uses, on bona-fide windows from frame_events plus recorded attack windows (or the labelled proxy corpus when none exist). APCER reads null — never a fabricated zero — when there is no attack data. Apply a value in the Policy tab; docs/configuration.md explains how to read the table.
