MOSIP Face Liveness & PAD Service

Offline, vendor-independent face liveness and presentation-attack detection for the MOSIP Registration Client.

Get Started · Features · How It Works · API · Architecture · Configuration · Contributing

⚠️ Disclaimer

  • This is an independent / community project and is not an official MOSIP product. [CONFIRM: affiliation with MOSIP] — the repository is maintained at hrishi25-spec/MOSSIP-Vibe-Coded and its relation to the MOSIP organisation has not been confirmed.
  • The bundled liveness and PAD logic is NOT certified against any standard.
  • The shipped engines are mock / OpenCV-heuristic placeholders, not a trained or evaluated model. See Testing & Evaluation.
  • A real, ISO/IEC 30107-3 evaluated model is required before any production use. Do not deploy this as a security control in its current state.

🎯 Overview

This service verifies that the face in front of the camera belongs to a live person physically present — not a printed photo, a phone or monitor replay, or a replayed video. It is built for the MOSIP Registration Client and covers three workflows:

Workflow Purpose
Resident registration Confirm a resident's face at enrolment, before it enters the registry.
Operator authentication Confirm the operator logging in is physically present.
Supervisor authentication Confirm the supervisor approving registrations is physically present.

It is designed to run as a local process on the registration host so that liveness and PAD enforcement never depend on network availability. It consumes already-decoded frames, so it works with any compliant L0/L1 device without touching the device protocol.

The active codebase is a Java 17 / Spring Boot 3 REST service. A Python FastAPI implementation of the same contract is kept for reference (see Python Reference Implementation).

✨ Key Features

  • Passive liveness first — a per-frame confidence score with temporal median voting (median, not mean, so a single blurred frame cannot swing the verdict).
  • Randomized active challenges — a challenge is selected with SecureRandom from the configured pool and never repeats back-to-back while alternatives remain.
  • Terminal PAD — a detected presentation attack fails the session immediately, with a distinct audit event. There is no retry after a PAD hit.
  • Per-workflow policy overrides — resident, operator and supervisor policies are stored per workflow and can be updated at runtime without a redeploy.
  • Offline-first design — all checks run locally; no mandatory cloud call.
  • Generic user messages — responses never reveal why a frame failed (print vs. screen vs. video), so attackers cannot probe the detector.
  • Audit trail and metrics — every decision is persisted to audit_logs; anonymized operational metrics are exposed at /api/v1/metrics.
  • Pluggable backends — a LivenessBackend SPI allows a mock, a TFLite MiniFASNet model, a MediaPipe FaceMesh model, or a vendor SDK to be swapped in without touching the API or UI.
  • Device adapters — vendor-agnostic frame sources for SBI L1 streams, L0 burst capture, and a mock device.
  • Evaluation harness — an ISO/IEC 30107-style APCER/BPCER/ACER harness (AttackScenarioHarness) that runs labeled presentations through the real engine pipeline.

🧠 How It Works

flowchart TD
    A["POST /api/v1/sessions<br/>workflow: RESIDENT | OPERATOR | SUPERVISOR"] --> B["POST /api/v1/sessions/{id}/frames"]
    B --> C{"Face detected?"}
    C -- "no / multiple" --> B
    C -- "yes" --> D["PAD check (every frame)"]
    D -- "attack" --> R1["action: reject<br/>session: FAILED"]
    D -- "bona fide" --> E["Passive liveness score"]
    E --> F{"score >= threshold?"}
    F -- "yes" --> P["action: proceed<br/>session: PASSED"]
    F -- "no" --> G["Issue randomized challenge"]
    G --> H["POST /api/v1/sessions/{id}/challenges/validate"]
    H --> I{"Challenge passed?"}
    I -- "yes, more required" --> G
    I -- "yes, enough" --> P
    I -- "no, retries left" --> G
    I -- "no, retries exhausted" --> R2["action: reject<br/>session: FAILED"]

Numbered walkthrough

  1. Create a session with a workflow, a deviceId and an optional subjectRef. The DB policy row for that workflow is resolved on every call.
  2. Stream frames (POST /api/v1/sessions/{id}/frames). Each frame is decoded (base64 → OpenCV Mat), the face is detected, and PAD runs on every frame. If the face is missing or duplicated the response asks the client to retry passively.
  3. PAD gate — an attack verdict fails the session immediately (action: reject, distinct audit event).
  4. Passive score — at or above passiveThreshold the session passes (action: proceed); below it the session moves to the ACTIVE stage and a challenge is issued (action: escalate_to_active).
  5. Validate and resolve (POST .../challenges/validate) with a frame burst. PAD runs across the burst first, then the action is evaluated: enough passed challenges pass the session, otherwise the client receives a fresh challenge (action: retry_challenge) or, once retries are exhausted, a rejection (action: reject).

Session states and terminal states

Kind Value Meaning
Status ACTIVE Open and accepting frames.
Status PASSED Liveness verified (terminal).
Status FAILED Rejected — PAD attack, retries exhausted, or passive fail with active disabled (terminal).
Status EXPIRED Closed by the client before a verdict (terminal).
Stage PASSIVE Single-frame passive scoring + PAD.
Stage ACTIVE Challenge-response window.
Stage COMPLETED Session reached a verdict.

🚀 Quick Start

Prerequisites — JDK 17+ (verified on JDK 21). Maven is not required if you use the bundled wrapper (./mvnw) or scripts/start.sh. Docker is optional.

All three options serve the API on port 8000 by default (SERVER_PORT overrides it). Once running:

  • Browser console — http://localhost:8000/
  • Swagger UI — http://localhost:8000/swagger-ui/index.html
  • Health — http://localhost:8000/health

Option 1 — Docker (PostgreSQL + API)

The Dockerfile copies a pre-built jar (COPY target/pad-liveness-backend-*.jar app.jar) and is not multi-stage, so you must build the jar before docker compose can build the image:

./mvnw clean package            # produces target/pad-liveness-backend-1.0.0-SNAPSHOT.jar
cp .env.example .env            # edit POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB
docker compose up --build       # PostgreSQL 16 + API on http://localhost:8000

⚠️ The base image is eclipse-temurin:17-jre-alpine, which is musl-based. The native OpenCV library bundled by org.openpnp:opencv:4.9.0-0 is a glibc build (it needs libc.so.6, libstdc++.so.6, libgcc_s.so.1 and ld-linux-x86-64.so.2). On Alpine it therefore fails to load: the service still starts, but /health reports "engine":"unavailable" and every frame endpoint returns 503. To make OpenCV work in Docker, switch the base image to a glibc variant (e.g. eclipse-temurin:17-jre) — [CONFIRM: verify the base image before publishing Docker as fully working].

Option 2 — JAR with PostgreSQL (default profile)

./mvnw clean package
POSTGRES_HOST=localhost POSTGRES_USER=mosip POSTGRES_PASSWORD=change_me POSTGRES_DB=pad_liveness \
  java -jar target/pad-liveness-backend-1.0.0-SNAPSHOT.jar

With the default profile, Flyway applies db/migration/V1__init_schema.sql on startup and Hibernate only validates the schema (ddl-auto: validate).

Option 3 — Dev profile with H2 (no database, no Docker)

./mvnw clean package
java -jar target/pad-liveness-backend-1.0.0-SNAPSHOT.jar --spring.profiles.active=dev

The dev profile uses an in-memory H2 database (schema created by Hibernate, Flyway disabled) and enables the H2 console at /h2-console.

One command (start.sh / start.bat)

scripts/start.sh builds if needed, starts the service, waits for /health, then opens the console. Verified flags: --no-build, --rebuild, --test, --port N, --profile NAME, --no-browser; the default profile is dev (H2). Run ./scripts/start.sh.

End-to-end example (curl)

# 1. Create a session
SESSION_ID=$(curl -s -X POST localhost:8000/api/v1/sessions \
  -H "Content-Type: application/json" \
  -d '{"workflowType":"RESIDENT","deviceId":"L1-CAM-01"}' \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['id'])")

# 2. Submit a frame (base64 JPEG). Repeat until action != retry_passive.
curl -s -X POST localhost:8000/api/v1/sessions/$SESSION_ID/frames \
  -H "Content-Type: application/json" \
  -d "{\"frameBase64\":\"$(base64 -w0 face.jpg)\"}"
# -> {"stage":"PASSIVE","action":"proceed", ...}                     (passed)
# -> {"stage":"ACTIVE","action":"escalate_to_active","challenge":{...}} (needs a challenge)

# 3. If escalated: validate the challenge with a short burst of frames
curl -s -X POST localhost:8000/api/v1/sessions/$SESSION_ID/challenges/validate \
  -H "Content-Type: application/json" \
  -d "{\"challengeId\":\"<from previous response>\",\"framesBase64\":[\"<f1>\",\"<f2>\",\"<f3>\"]}"
# -> {"passed":true,"action":"proceed"} | {"passed":false,"action":"retry_challenge"} | {"action":"reject"}

# 4. Fetch the audit trail
curl -s localhost:8000/api/v1/sessions/$SESSION_ID/audit

face.jpg must contain a detectable face; without the vendored Haar cascades in src/main/resources/ no frame can pass (see Architecture).

⚙️ Configuration

Two configuration systems exist and populate the same EffectivePolicy shape from different sources. Know which one you are changing.

Source Where Defaults Used by
Engine / library defaults LivenessConfig + AppConfig (mosip.liveness.* in application.yml) threshold 0.80, min challenges 2, timeout 10000 ms, retries 2 Embedded engine (FaceLivenessEngine), tests, harness
DB policy defaults config_policies seed in V1__init_schema.sql and ConfigController.getOrCreatePolicy() threshold 0.75, min challenges 1, timeout 8000 ms, retries 3, failure LOCK, challenges [blink, smile, turn_left, turn_right] The REST API decision path

The REST path (DecisionEngineService) reads EffectivePolicy from the DB row via ConfigService on every call. Fields the DB does not store are filled with hard-coded engine fallbacks: minFaceQuality 0.50, passiveMinFrames 5, passiveWindowFrames 7, maxSessionDurationMs 30000, frameSamplingRate 2, frameSamplingMinFps 15, combinedPassiveWeight 0.4, combinedActiveWeight 0.6.

⚠️ The LivenessConfig and MockLivenessBackend Spring beans are created by AppConfig but are not consumed by the REST services — the REST path scores frames with OpenCV heuristics in LivenessEngineService / PadEngineService directly. [CONFIRM: whether the two config systems should be unified]

Per-workflow policy fields

Full config policy reference | Field | Type | Range / values | DB default | Engine default | |-------|------|----------------|-----------|----------------| | `livenessEnabled` | boolean | `true` / `false` | `true` | `true` | | `passiveThreshold` | double | 0.0 – 1.0 | `0.75` | `0.80` | | `activeLivenessEnabled` | boolean | `true` / `false` | `true` | `true` | | `minChallengeCount` | int | 1 – 5 | `1` | `2` | | `challengeTypes` | string[] | challenge names | `["blink","smile","turn_left","turn_right"]` | all types | | `challengeTimeoutMs` | int | 1000 – 60000 | `8000` | `10000` | | `maxRetryCount` | int | 0 – 10 | `3` | `2` | | `onRepeatedFailure` | string | `LOCK` \| `ESCALATE` \| `ALLOW_RETRY` | `LOCK` | `LOCK_OUT` | | `minFaceQuality` | double | 0.0 – 1.0 | — (not stored) | `0.50` | | `passiveMinFrames` | int | ≥ 1 | — (not stored) | `5` | | `passiveWindowFrames` | int | ≥ `passiveMinFrames` | — (not stored) | `7` |

Changing policy at runtime

PUT /api/v1/config/{workflowType} updates the stored row; the decision engine re-reads it on the next call, so no redeploy is required. Values are validated and rejected with 400 when out of range (e.g. passiveThreshold outside [0,1], challengeTimeoutMs < 1000).

curl -X PUT localhost:8000/api/v1/config/SUPERVISOR \
  -H "Content-Type: application/json" \
  -d '{"passiveThreshold":0.90,"minChallengeCount":2,"maxRetryCount":1,"onRepeatedFailure":"LOCK"}'

Liveness backends

Backend Model file What it does When to use
MockLivenessBackend none Fully scriptable Subject (face, blink, smile, turn, PAD verdicts) with per-frame signal overrides. Unit tests, CI, the attack harness. This is the only backend wired as a Spring bean.

🎭 Challenge Types

Two evaluators exist with different mechanics. The REST path (DecisionEngineService → LivenessEngineService) evaluates challenges from OpenCV face/eye geometry; the engine path (ChallengeEvaluators) evaluates them from backend landmark signals.

Challenge criteria (engine path — ChallengeEvaluators) | Challenge | Pass criterion | Threshold constants | |-----------|----------------|---------------------| | `BLINK` | EAR drops below close value, then recovers above open value. | close `0.22`, open `0.27` | | `SMILE` | Smile score exceeds threshold at least once. | `0.55` | | `TURN_HEAD_LEFT` / `TURN_HEAD_RIGHT` | \|yaw\| reaches the target angle. | `12°` | | `LOOK_DIRECTION` / `LOOK_UP` / `LOOK_DOWN` / `LOOK_LEFT` / `LOOK_RIGHT` | Gaze within tolerance of the target for ≥ 50% of frames. | tolerance `0.35` | | (per-frame UI) | Action confirmed after N frames → `HOLD_STILL`. | `ACTION_CONFIRM_FRAMES = 2` |
Challenge criteria (REST path — LivenessEngineService) | Challenge (`models.enums.ChallengeType`) | Pass criterion | Threshold | |------------------------------------------|----------------|-----------| | `BLINK` | Eye cascade count reaches 0, then ≥ 1 in a later frame. | eye cascade | | `SMILE` | Mouth-ROI Laplacian variance range across frames exceeds a floor. | range > `50` | | `TURN_LEFT` / `TURN_RIGHT` | Face-box horizontal travel (egocentric mapping). | > `±15 px` | | `LOOK_LEFT` / `LOOK_RIGHT` | Face-box horizontal travel. | > `±10 px` | | `LOOK_DIRECTION` | \|face-box horizontal travel\| exceeds the gaze floor. | > `10 px` | | `LOOK_UP` / `LOOK_DOWN` | **Always fail closed** (vertical gaze is not recoverable from a horizontal face box). | `false` | **Note:** `LOOK_UP` and `LOOK_DOWN` can never pass in the REST path. Do not enable them for a workflow until vertical gaze tracking is implemented.

🔐 Security & Privacy

  • PAD is terminal. A presentation-attack verdict fails the session immediately, with a distinct PAD_REJECTED audit event. Retries are not offered.
  • Median, not mean. Temporal scoring uses the median of the sliding window so one anomalous frame cannot pass or fail a subject.
  • Randomized challenges. SecureRandom drives a shuffled bag so every allowed challenge appears before any repeats, and no challenge repeats back-to-back while alternatives remain.
  • No raw frames or model internals leave the process. Audit records and API responses contain decisions and scores, never frames, embeddings, or detector internals.
  • Generic failure messages. Every error maps through LivenessErrorCode.userMessage() (e.g. "Face verification could not be completed. Please try again."), so a client cannot learn which detector fired.
  • No PII in logs or device ids. Audit lines carry session id, workflow and decision fields only.

🔒 Security considerations

The API has no authentication or authorization. There is no Spring Security dependency and no key/token check on any endpoint — including PUT /api/v1/config/{workflowType}, which lets any caller rewrite policy. CORS is restricted to localhost / 127.0.0.1 origins only.

Until authentication is added, deploy this service only as a local or internal service bound to the registration host, and never expose it to an untrusted network. [CONFIRM: authentication requirements and threat model]

🧪 Testing & Evaluation

Running the tests

./mvnw test          # full suite
./mvnw clean package # build + full suite

The suite covers the engine state machine (pass, escalation, PAD blocking, error conditions), decision logic, all challenge evaluators and the selector, per-workflow config merging, every REST controller, the device adapter layer, entity persistence, and the attack harness. The most recent recorded Maven Surefire run reported 132 tests, 0 failures across 21 test classes. [CONFIRM: re-run ./mvnw test and update this count if it has changed]

ImageUtilsCascadeTest fails the build if the vendored Haar cascades are missing, so a build that silently disables face detection cannot pass.

The attack-scenario harness

AttackScenarioHarness generates labeled presentations — BONA_FIDE, PRINTED_PHOTO, SCREEN_REPLAY, VIDEO_REPLAY — runs them end-to-end through the real FaceLivenessEngine, and reports APCER, BPCER, ACER (plus escalation rate) via PadMetrics.

⚠️ These numbers are not a measure of real model accuracy. The harness uses MockLivenessBackend with configured, simulated imperfection rates — a 3% attack-miss rate and a 1% bona-fide false-positive rate (SIMULATED_ATTACK_MISS_RATE, SIMULATED_BONAFIDE_FP_RATE). It validates orchestration (PAD terminality, escalation, retries), not detection performance. Reporting them as ISO/IEC 30107-3 results would be misleading.

ISO/IEC 30107 alignment means taxonomy- and telemetry-aligned: PAD runs per frame, attack types map to the standard's species, and structured telemetry supports APCER/BPCER computation. Certification is not claimed and has not been performed.

For real numbers, swap in a real backend and a labeled corpus of physical presentations, then run the harness against it. No such corpus ships with this repository.

🔧 Extending the Project

Add a backend

  1. Implement LivenessBackend (id, initialize, analyzeFrame, scorePassiveLiveness, assessPad, shutdown).
  2. Return it from AppConfig#livenessBackend() (or inject it where the engine is constructed).
  3. No engine, UI or config changes are required.

Add a challenge type

  1. Add the value to core.ChallengeType and models.enums.ChallengeType.
  2. Add an evaluator branch in ChallengeEvaluators (batch + per-frame) and/or LivenessEngineService.
  3. Generate any parameters in ChallengeSelector.parametersFor().

Add a workflow

  1. Add the value to core.WorkflowType and models.enums.WorkflowType.
  2. Map it in ConfigService.toCoreWorkflow / toDbWorkflow.
  3. Add a seed row in a new Flyway migration and, if needed, a LivenessPolicy override.

Add a device adapter

  1. Implement DeviceAdapter (open → startCapture → stopCapture → close).
  2. Return a DeviceCapabilities that describes streaming vs. burst capture.
  3. Deliver normalized Frame objects to the FrameListener.

  • Keep user-facing error messages generic and never log raw frames or PII.
